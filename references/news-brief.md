# 每日新闻 / 早报的领域覆盖

仅在需求访谈的任务是新闻汇总或早报时加载。本文件提供寻找缺口的视角，不是预装订阅偏好，不要求每个人关心同样的类别。

## 从已有条件出发

对“每天早上 8:30 从我指定的一些来源推送新闻，类别还没列全”，可提取：

- 每日、8:30、新闻推送是已给条件；通常每日包括周末，不重复询问。
- 具体来源清单若不在上下文中，仍为未知；“指定”不自动等于“只能”或“优先”。
- 时区、推送目的、内容范围和目的地若没有给出，记录缺口。
- “8:30 给我推送”偏向交付时刻；需判断平台能否提前采集。如果只能在 8:30 启动，应明确差异，不能承诺准点送达。

用途不明确时，首问可为：“每天看完这份早报，你最希望它帮助你做什么判断，或省下哪部分时间？”这是同一用途问题，用户选一种表达回答即可。用途已知时直接探索最影响覆盖的缺口。

## 按用途生成候选类别

先复述用户已有类别，再提出少量相邻遗漏项，每项给一句与用途的关系。以下为示例，不是默认栏目：

| 用户用途 | 可考虑的覆盖视角 |
| --- | --- |
| 了解世界与公共事务 | 地域与国际事件、政策与社会、科技、环境等 |
| 技术学习或研发选型 | 发布与能力变化、价格/接口变更、工具生态、研究、服务故障或安全通告 |
| 跟踪行业与竞争 | 目标企业、产品、经营数据、产业链、政策、客户与市场变化 |
| 寻找写作选题 | 用户关心的主题、社会事件、不同观点、长期趋势与背景材料 |

不能因“新闻”默认加入财经或投资；不能因“AI”只覆盖模型发布；不能因热门就默认加入融资、人物八卦或传闻。

对照已有类别，问“纳入 / 排除 / 可选 / 后续再看”中的一个实际选择。地域、公司、来源和新闻类别是不同维度，避免把它们挤成同一层分类。只有用户明确接受，或明确授权你代定的范围内，候选项才成为执行内容。

遇到“尽量全面”，先理解是覆盖更多主题、更多来源还是不漏重大事件；不要强制每类每天至少一条。缺少当日重大新闻时允许零条或精简版，具体空结果策略可由用户选择或授权代定。

## 范围、质量和交付

根据任务规模检查关键项；非关键项给出可修改默认方案或暂缓，避免逐条盘问：

- 来源：实际网站/RSS/账号及地址；严格白名单还是优先来源；是否允许交叉核实与引用外部来源。分类补齐不等于自动扩大来源许可。
- 语言和地域：原始报道语言与最终输出语言分开；企业/领域范围不要由用户所在时区推断。
- 时间窗口：过去若干小时、上次成功汇总以来等；区分事件发生时间、报道发布时间和更新内容，避免旧闻当新事。
- 入选规则：用户用途下的相关性与重要性；发布公告、分析、观点、传闻分别处理。
- 去重排序：同一事件多源合并、优先原始材料；是否允许后续新进展再次入选。
- 证据：每条链接和日期；必要核实的强度。严格来源限制下不能为交叉验证擅自越界；无法验证时按已确定的降级策略处理。
- 数量与篇幅：总上限、分类优先级、单条结构、阅读时间；不以凑足数量牺牲筛选。
- 调度：时区、每日频率、预期交付还是开始采集、长任务与补发策略；精确按时送达需要实际平台能力支持。
- 推送：当前对话、应用通知或其他已指定渠道及收件人；生成结果、通知提醒和外部发送不是同一能力。
- 异常：无重要新闻、部分来源失败、全部失败、重复任务/重复消息；给出有界重试或后续处理，不无限重试、不编造内容。
- 成本/访问：免费或可用订阅、登录和抓取权限；不暗示自动突破付费限制或购买服务。

## 形成验收

从已确认的要求写可观察的验收，不用“全面、优质、及时”代替标准。例如当用户确认了对应条件后，可以写：

- 输出满足约定的时区与触发/交付时间语义；
- 每条有支持摘要的真实来源链接和时间信息；
- 范围外主题不出现，同一事件按约定合并；
- 总条数和篇幅不超限，无可选内容时不凑数；
- 来源故障、空结果按约定提示，不冒充完整采集。

这些例子均需绑定实际需求，不能自动视为已经答应的规格。读取 [task-card.md](task-card.md) 输出卡片；仅基于最初一句话时，应交付 DRAFT，并列明来源清单等关键未知。
