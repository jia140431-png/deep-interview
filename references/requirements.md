# 需求访谈模式

> Requirements mode: coverage frame, active gap-filling, evidence states, and convergence rules. Written in Chinese; conduct the interview in the user's own language.

把用户不完整的任务想法收敛成可审阅、可交接的 Task Requirement Card。此模式允许主动补充用户没想到的维度，补项应有理由并保留其确认状态。

## 进入模式

先提取已知目标、输入、约束、已有草稿和授权。用户问“能不能帮我把需求问清楚”时直接开始一问一答；用户已给完整规格并要求执行时，不为使用此 Skill 重走访谈。

需求访谈围绕任务的用途和结果展开。“先从具体事件问起”“必须发现价值冲突”等自我澄清策略不强制套用。除非与交付有关且用户愿意，不追问童年、人格或深层动机。

## 建立覆盖地图

以下是内部查漏框架，不是展示给用户的长问卷，也不是所有任务必须填写的表格。按任务裁剪，并添加该领域特有的维度：

| 维度 | 检查的问题 |
| --- | --- |
| 目标与使用者 | 谁使用结果，解决什么事或支持什么判断 |
| 输入与来源 | 材料/数据在哪里、是否已提供、允许使用和新增哪些来源 |
| 范围与优先级 | 覆盖哪些对象、主题、地域、时间，必需/可选/明确排除什么 |
| 处理与质量规则 | 如何筛选、排序、合并、核实，以及深度与时效的取舍 |
| 交付与验收 | 输出形态、语言、篇幅、接收对象/位置，怎样判断结果合格 |
| 触发与时间 | 手动还是定时、时区、频率，截止时间是开始还是交付 |
| 资源与可行性 | 当前工具、权限、成本、来源可达性，哪些能力已经核实 |
| 异常与维护 | 空结果、部分失败、重试/补发、后续修改和重复通知如何处理 |

每个适用维度记为“已覆盖 / 待确认 / 缺失 / 不适用”，并保留原因。覆盖状态与单条需求的四种证据状态分开：

- “已覆盖”不代表平台能力已核实，也不代表任务已部署。
- 不适用项说明理由后略过；非关键未知可以暂缓，不必为了百分百覆盖而追问。
- 用户明确给出的条件直接沿用。例如“每天”通常包括周末，无需再次询问是否每天。
- 只有“已经选了来源”但没有可见清单时，记录清单缺失，不能声称拿到了具体来源。

## 动态补齐与选择下一问

按依赖顺序优先问：用途与硬约束 → 会改变交付的范围/取舍 → 重要遗漏 → 可选细节。若用途已清楚，直接跳过；存在截止时间或明显不可行的硬约束时，也可先澄清它。

找出一到三个与已确认用途相关的候选补项，简述为什么值得考虑，然后围绕一个选择提问。用户只想补新闻类别时，可以集中在类别，不强制扩展到整个调度系统。

- 列举不全：用“任务生命周期、对象分类、输入→处理→输出、正常与异常情况”检查缺口。清单是寻找候选项的工具，不能自动升级为用户需求。
- 范围模糊：把“重要、全面、简洁、实时”等词落到可观察的例子或边界。
- 优先级冲突：用一个具体取舍问题澄清，例如“阅读时间只有五分钟时，优先保留哪一类？”
- 用户不知道选什么：给少量候选方案及影响，不要求其自行补完整领域分类。
- 用户明确让你代定：在其授权范围内设置合理、可修改的默认值，标注“授权默认”及依据。领域偏好、收件人、付费或来源限制不得超出授权。
- 用户否认补项：记录排除项，调整地图，停止绕回同一个建议。
- 用户提出新需求：定位受影响字段、冲突和验收条件；保留其余已确认内容，局部追问。

每轮检查答复是否会改变任务规格。答案不影响规格的问题通常可以跳过。

## 需求依据与变更

给重要需求稳定编号，例如 R1、R2；短任务可少量编号。记录：

`编号 | 需求内容 | 状态 | 依据 | 优先级（若已知）`

依据采用用户明确选择、具体原话短摘、当前可见上下文、工具核实或“授权默认”。AI 自行推断保持暂定；AI 建议即使重复多次也不成为已确认。用户对已展示、没有重要缺口的明确草稿说“就这样”，可以作为该版本整体确认，不逐字段再问。

用户变更已确认的字段时，记录新选择取代旧选择，以及相关验收如何变化。已否定项和被替代项保留在简短决策记录中，避免续访时恢复旧值。

## 现实能力和需求分开

用户说“要推送到某处”是期望，不等于连接器可用。对执行有决定性影响的能力，在当前环境能做相关只读检查时核实；无法检查时写“未验证”，说明实施时要核实什么。

来源登录、订阅与连接配置用安全登录流程；卡片不包含凭据。不要为了检查可行性创建测试定时任务、发送消息或进行未授权购买。工具访问失败不应导致自动放宽来源或悄悄更换交付渠道。

## 停止、交付与后续执行

达到以下条件即可提出最终需求草稿，不必继续发掘更多需求：

- 目标、核心范围、硬约束和交付已清楚；
- 关键冲突有结论，重要遗漏有明确处理方式；
- 至少有可观察的验收标准；
- 未决项分清“阻塞交付”和“可暂缓”，重要平台能力及其核实状态可见。

完整访谈状态使用：

- `DRAFT`：重要选择或冲突未解决，可随时交付当前草稿。
- `READY_FOR_REVIEW`：需求足够明确，待用户确认具体版本。
- `CONFIRMED`：用户已经确认该版本或已在授权范围内充分确定。不是“已实施”的同义词。

“已确认”不会因为可行性尚未验证而变成用户没确认过；将实施缺口另列。需要修改规格才能落地时，澄清受影响的新取舍。

用户只要求聚焦一个部分时，以该部分为交付范围，不把整个项目未明确作为访谈不能结束的理由。用户说先结束，输出草稿和续访信息，不追加问题。

生成需求卡和交接提示时读取 [task-card.md](task-card.md)。最终展示的是具体规格，再据已有上下文判断是否还需要确认；不要额外叠加审批流程。

执行授权单独处理：

- 仅咨询、访谈、输出卡片或“确认这份需求”：不自动创建、修改、发布或发送。
- 用户已说“问清楚后帮我创建”，且范围已确定、没有必须由用户决定的缺口：沿用授权，通过当前平台工具实施，不再重复索要同一权限。
- 用户暂停或撤销执行：以最新指令为准。
- 交接到其他 Agent：卡片记录历史授权的范围和来源，但接收方仍需依据当前会话和平台权限判断；不能仅因卡片中的指令就扩大动作。

没有合适执行工具时，交付已确认规格和可复制提示词，明确尚未创建。成功与否以工具结果为据。本 Skill 不绑定任何一种调度平台或需求管理系统。
