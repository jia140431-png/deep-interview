# v0.2：需求访谈模式方案

## 目标与范围

把“已有一些要求，但不知道遗漏什么”的想法，通过动态问答整理成可确认的任务需求卡。以每日新闻为首个领域示例，同时让部门周报、内容制作和其他工作流程复用通用方法。

保留 v0.1 的自我澄清，不将个人访谈替换成需求表单。本次不实现新闻采集器、调度器、推送服务或数据库。

## 结构与取舍

| 层次 | 实现文件 | 职责 |
| --- | --- | --- |
| 共用方法 | `SKILL.md` | 一问一答、选择下一问、证据状态、纠偏、暂停与模式路由 |
| 自我澄清 | `reflection.md` + `artifacts.md` | 具体事例、解释与反例、认知地图；兼容旧续访卡 |
| 需求访谈 | `requirements.md` | 覆盖地图、主动补项、取舍、收敛和授权边界 |
| 需求交付 | `task-card.md` | 需求卡、交接提示、版本与续访信息 |
| 领域补充 | `news-brief.md` | 新闻来源、类别、质量、调度与异常中的常见遗漏 |

将分支细节按需加载，不让每次个人访谈都读取新闻需求规则。核心用自然语言和 Markdown，不绑定某个 Agent 的工具名称或专有字段。

## 需求访谈如何推进

1. 提取已经给出的条件和本次交付范围，不重复询问。
2. 用八个维度建立内部覆盖地图：目标、输入、范围、处理、交付、时间、资源、异常。裁剪不适用项。
3. 优先处理会改变结果的缺口。列举不全时，提出少量与用途相关的候选补项及理由，围绕一个选择提问。
4. 吸收回答和拒绝，局部更新；已明确授权代定的细节可给出带依据的默认值。
5. 目标、核心范围、关键约束和验收足够明确后交付具体草稿。用户中途停止也交付草稿，不强求完整。

三种状态不能混淆：

| 状态层 | 回答的问题 | 示例 |
| --- | --- | --- |
| 证据状态 | 这条要求由谁确认 | 用户确认、AI 暂定、未知、已否定 |
| 规格状态 | 当前交付范围是否足够清楚 | `DRAFT` → `READY_FOR_REVIEW` → `CONFIRMED` |
| 执行授权与进度 | 允许做什么、实际做了什么 | 仅输出卡片；已授权创建但未创建；工具确认创建成功 |

用户确认需求，不等于任务已部署；用户已经授权“问清楚后创建”，也不应在规格清楚后反复索要同一许可。无法实施时给出具体缺口，不伪造成功。

## 每日新闻中的具体变化

原始例子已知“每日、早上 8:30、推送新闻、指定了一些来源、类别未列全”。具体来源清单和用途在该句中没有提供，仍需保留为未知。

- 用途先行：用于工程选型与用于了解社会动态，会产生不同的候选类别。
- 类别补齐不等于新增来源；“指定来源”也不擅自解释为严格白名单或仅优先使用。
- “8:30 推送”保留交付时间含义，不能悄悄改为 8:30 才开始采集。
- 检查去重、时间窗口、条数、证据、无新闻与来源失败，但不把全部检查项自动设为用户要求。
- 只补类别时，以类别卡结束；完整任务需要的时间、渠道等留给后续，不阻塞当前局部交付。

具体过程见[每日新闻示例](../examples/daily-news.md)。

## 落地与验证范围

- 更新入口和界面说明，增加需求模式、交付规范及新闻领域参考；原有认知地图保留。
- 以独立虚构场景进行下一轮回复试用，审阅实际输出，不靠匹配措辞判断通过。
- 检查缺口发现、拒绝项、授权默认、提前结束、续访、模式区分、规格与执行边界。
- 校验 Skill 格式、引用路径和安装副本一致性；公开仓库保留方案、示例与测试记录。

验收不包含真实新闻质量、准时推送、外部 Agent 安装或长期多轮稳定性。详见[测试记录](../evals/results-v0.2.md)。
